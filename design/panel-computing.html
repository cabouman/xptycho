Computing: the panel's recommendation

Recommendation

Build the design now on the computing page. Every large array is sharded: the per-position arrays by position, the object image by row into bands with one owner each. Each GPU adds its patches into the rows they touch (its window), the pieces go to the bands' owners to be summed, and each GPU copies back the finished rows it needs. These are mbirtorch's two operations, and they serve every step. A reviewer walked an iteration on three GPUs by hand and found every pixel receives every contribution exactly once; a small numerical test agrees to \(7 \times 10^{-16}\) in double precision.

Six Opus members reviewed the earlier page independently on 2026-10-03; Vera and a seventh, fresh reviewer then attacked the draft of this recommendation. The comparison of the two ways to shard the image that the panel raised is drawn on the bands or windows page.

Decided by Charlie, 2026-10-03

1: bands with owners. 2: the grid correction stands. 3: the baseline runs wait until the tests are written. 4: yes, after the match. 5: yes; configure_devices is documented on the computing page, section 4.

The five questions, as asked

1.Bands with owners, or windows only? The page uses bands with owners, which is mbirtorch's pattern. Vera proposes a simpler form: no bands; each GPU keeps only its window, and GPUs whose windows overlap exchange and add the overlapping rows.
Windows only: one image operation instead of two, less image memory per GPU, and only overlapping rows move. But it needs a rule for sums over the whole image (which GPU counts a shared row), and it departs from mbirtorch. Claude recommends bands with owners: one owner per pixel makes the whole-image sums and the final image need no extra rule, it was the form checked by hand, and it is what an mbirtorch reader already knows. Exchange is under 0.1% of an iteration either way.
2.The object grid. The theory page said the grid is the union of the patches. In the old code the grid is a given size and includes pixels no patch reaches (gold balls: 613 rows, patches cover rows 10 to 566). Those pixels enter the starting image's median and one of the small constants, so matching the old code requires the old grid.
I corrected the theory and objects pages. Confirm.
3.Authorize four runs of the old code? The tests need baselines that do not exist yet: the blind two-mode run on the paper's data (its 467 MB download was paused on 2026-09-27), a tiny blind two-mode case, the first three iterates of the blind single-mode run, and the tiny baseline repeated in double precision, which measures how far single-precision results can be expected to differ.
All run on the Mac in the old code's environment, a few minutes each except the first. Nothing runs without your yes.
4.After the new code matches the old: adopt two changes? Update \(v\) and the probe copies in place, which drops the \(w\) and \(r\) arrays and fits 1.9 times as many positions per GPU. And compute each distinct Fourier transform once: the old code takes 18 per position per iteration with two modes, where 12 are needed.
Both are the same algebra and change only the last digits. The panel is unanimous: yes, but only after the match.
5.Match mbirtorch's settings? configure_devices(num_devices=1, devices=None) as in mbirtorch, with the batch size as a model parameter instead of an argument there.
This changes one line of the objects page. Recommended.

Tests the panel proposes

Three fast tests on CPU and one script for a GPU node: the tiny baseline on one device against the old code; two and three devices against one, with a block boundary inside a scan line; a tiny blind two-mode case; and, on a GPU node, the gold balls on 1, 2, and 4 GPUs, with a check that the probe modes are identical on every GPU.
